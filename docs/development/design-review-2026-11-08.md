# AgentForge v0.1.7 设计审查

结论：**不批准（Not approved）**。已有紧凑桌面语言与组件体系，但失败恢复的焦点组织、Tab 键盘行为尚未达到本次要求。不能用“控件已经等高”代替设计完成。

此次只审查、提出决策，不实施视觉重做。数据根目录整理属于另一个已授权功能改动，不算修复了本文的视觉问题。

## 范围与意图

审查对象为本机 v0.1.7（源码基线 `02c4351`），不是整个提交历史的代码风格。目标用户是一位同时管理任务、员工与本机模型的操作者；首要动作是判断任务是否需要介入、推进或恢复执行，然后阅读协作结果与证据。界面应当紧凑、安静、适合长时间阅读，保留已有蓝灰表面、系统字体、语义状态和员工身份色。

基准为 `.interface-design/system.md` 和 `docs/06-design-system.md`。因此不把系统字体、32px 目录控件、无投影的边线式层次、多色身份头像、暖白侧栏、短表格不填满窗口等已确定的选择列成缺陷；也不要求添加大标题、营销卡片或装饰渐变。

实际证据：当前安装版失败任务的整屏观察；同一安装包在隔离 HOME 中的 1320×850 极简与 760×600 暖白界面，覆盖任务、员工、角色、团队、工作流、自动化、插件/MCP 目录、常规/Runtime/工作目录设置共 22 个页面状态，以及任务创建、工作流节点编辑弹窗。画布等待真正就绪后再观察，未把加载帧当最终设计。Tab 键盘另在隔离暂停 Run 中复现。截图与测量留在忽略的 `.data/design-review-20261108-cHntmO/`，键盘结果在 `.data/design-review-20261108-qyPc7Z/evidence.json`；没有向真实任务发送消息。

限制：市场截图主要覆盖空态，实际 MCP 工具明细、员工资料与全部 Provider 故障状态没有逐项实机覆盖；相关代码只用于检查组件复用，不能宣称这些状态全部验收。不是屏幕阅读器完整认证或业务功能验收。

## 先看整体

目录页能辨认“查找 → 名称 → 状态 → 操作”，设置页也有稳定的主/子标题，品牌和身份头像具有产品识别。主要问题集中在进入工作之后：真正需要人做决定时，多个操作没有明显让位；员工目录为了容纳可选内容预留整块空白；短窗口的必选配置与保存操作分离。整体并非没有体系，但少数关键场景仍在使用默认布局分配注意力。

## 按影响排序的发现

### B1 · Blocker：失败页把技术错误与无关操作同时推到前台

**默认了什么**：任务页直接展开英文 `ENOSPC` 和完整内部 JSON 路径；恢复按钮为琥珀描边，终止为红字描边，而下方“全部”筛选是更显眼的实心蓝。用户需要恢复任务，最抢眼的可点击元素却是过滤器。标题、错误区、三层状态说明和右侧元信息同时争夺首屏。

**代价**：必须先解读底层异常，再在不同区域找操作；界面没有把“现在应该做什么”组织成唯一焦点。新增更多颜色或把错误字变大不能解决。

**应做的决定**：失败状态以“原因摘要 + 原失败员工 + 一个恢复主操作”为焦点；原始路径、调用堆栈和诊断证据由控制台/详情承接。将“全部/涉及人类”降为轻量分段控件，终止继续保持次级危险操作。恢复入口必须说明恢复的是谁，而不仅是流程节点；不要自动执行恢复，也不改变业务状态。

**验收**：遮住所有正文，仍能在第一眼指出唯一恢复操作；长异常不会挤压协作内容，详细诊断仍可定位。

位置：`web/app.js` 的 `renderWorkspace`（约 1064 行）、`workspaceTopActions` 和 `renderCollaboration`；`web/styles.css .workspace-failure/.collaboration-toolbar`，宿主覆盖位于 `apps/electron/compact.css`。

### B2 · Blocker：任务 Tab 声明了语义，却没有实现完整键盘模型

**默认了什么**：三个 `role="tab"` 均为 `tabIndex=0`，只有点击切换。聚焦“协作记录”按 ArrowRight 后，焦点和选中项均保持原处；三个页签都占普通 Tab 停靠点。自动化详情采用同类手写页签，代码未提供对应方向键处理。

**代价**：外观告诉用户这是 Tab，实际键盘行为却是三枚独立按钮；辅助技术和熟悉桌面键盘导航的用户得到不一致的模型。这是交互缺口，不是审美偏好。

**应做的决定**：统一共享 Tab 行为：活动项是唯一 Tab 入口，左右键/Home/End 移动并按明确模式激活；焦点、`aria-selected`、`aria-controls` 和面板名称同步。插件详情已经有正确方向键与 roving tabindex，可抽取复用其行为，不另建第二套控件，也不强行引入框架。

**验收**：任务、自动化、插件详情三处按同一键序得到相同行为；面板切换和数据刷新后焦点仍可预测。

位置：`web/app.js:1065`、全局 `data-ws-tab` 点击处理；`web/automations.mjs:23`；已有参考 `web/marketplace.mjs` 的 `data-plugin-tab` 键盘处理。

### S1 · Should-fix：员工卡片把“可能有的内容”变成永久空槽

**默认了什么**：简介固定三行高度，能力区固定 42px，即使没有标签也占位置；简短简介与底部元信息之间留下多行空白。带角色的一张卡片又比同排其他卡片多一条内容，操作行的基线发生变化。

**代价**：屏幕更多用于展示空槽和重复边框，查找员工需要滚动更多；卡片的视觉重量来自占地，而不是姓名和能力。

**应做的决定**：保留头像/姓名/可用的顶部结构，将卡片组织成身份、简介、底部运行配置三个固定层级；可选标签按实际内容出现，同排操作在一致的底部轨道。通过统一内容上限维持整齐，不用空标签区撑高度，也不改成杂乱的瀑布流。

**验收**：无标签、多个标签、带角色和长名称四种卡片同屏时，姓名与主操作轨道稳定，空内容不产生一整条空带。

位置：`web/styles.css:393–403`（简介 `height:calc(3 * 1.6em)`、`.capabilities height:42px`）、`apps/electron/compact.css` 员工卡片覆盖；`web/app.js renderAgents`。

### S2 · Should-fix：长工作流名称把属性标签带到错误的基线

**默认了什么**：`workspace-properties` 用 `align-items:baseline`；值是一个可换行的内联 button。长名称换行时，按钮的基线来自末行，“工作流”标签看起来垂直落在名称中间，末尾的 ↗ 还会单独占一行。

**代价**：最基础的“标签：值”关系需要重新辨认；短名称截图正常，真实长名称就暴露了结构问题。

**应做的决定**：属性行采用稳定的首行对齐；链接文本允许换行，外链图标作为不可拆散的尾部单元。统一属性键宽与值的行高，不用针对某一个标题加负 margin。

**验收**：一、二、三行名称的标签都对齐第一行文字，↗ 不孤立成行，点击和键盘目标保持完整。

位置：`web/app.js workspaceDetailsMarkup`（约 961 行）；`web/styles.css:1579–1582、1842、2178`。

### S3 · Should-fix：工作目录动作残留旧的低对比度绿色

**默认了什么**：`.workspace-path button` 仍使用硬编码 `#8da24e`，没有进入当前品牌语义；“复制/打开”在白色工作面上的文字对比约 **2.83:1**。其尺寸又属于小字动作，比周围正文更难辨认。

**代价**：必要的文件入口像禁用注释；同时引入一条没有语义的旧绿色，破坏已确认的颜色体系。

**应做的决定**：复用共享文字动作及可访问的中性/强调 Token；路径本身是元数据，动作是可操作入口，二者要有稳定区别。局部文件预览可以保留用户选择的主题，不应影响外层路径动作。

**验收**：两主题下普通文字动作达到清晰可读的对比，hover/focus 可见；不改变文件预览主题。

位置：`web/styles.css:431–432、1846–1848`。

### S4 · Should-fix：团队状态泄露了内部枚举

**默认了什么**：团队列表把 `active` 直接放进状态胶囊，周围都是中文；数字员工已经显示“可用”。

**代价**：同一种可用状态出现两套语言，用户需要猜测团队 `active` 是否代表正在执行任务。蓝色本身没有问题，错误在内容语义。

**应做的决定**：团队复用员工的可用/停用呈现；内部枚举留给 API，状态标签只表达配置可用性，不暗示模型账号健康或任务运行。

**验收**：创建、停用、回读团队后，列表与员工目录使用一致中文状态。

位置：`web/app.js:546–556 renderTeams` 中的 `pill(team.status)` 与共享状态映射。

### S5 · Should-fix：短窗口先展示大块空正文，却把必选成员挡在首屏之外

**默认了什么**：760×600 的空任务弹窗里，正文输入占据约半个窗口；成员/模板只露出上边缘，底部提交操作却始终完整可见。滚动可以完成操作，但首屏看不出还有哪个必选输入未处理。

**代价**：用户点击“保存并开始”后才被迫寻找隐藏的成员与经理选择；同一表单显得像上下两个区域。

**应做的决定**：保留单一正文滚动区与固定操作区；短高度先保证必选配置的可见性，再在既有六至十二行范围内分配正文高度。滚动后聚焦错误字段并保留草稿，不把成员重新固定到底栏。

**验收**：760×600 空表单能辨认标题、正文和成员选择入口；长内容及多行成员仍在同一滚动容器，底栏不覆盖候选。

位置：`web/app.js newTaskModal`、`web/styles.css .task-create-modal/.modal-scroll/.task-form-content-row`、`apps/electron/compact.css` 短高度规则。

### S6 · Should-fix：窄窗口设置导航没有明确的分组节奏

**默认了什么**：760px 下八个分类呈现“第一行六个、第二行两个且分散到两处”，导航占去明显的垂直空间；“更新/运行日志”像两块游离内容，下面才出现当前设置。

**代价**：低频导航获得了与配置主体相近的占地，当前分类和可编辑内容的关系变弱。

**应做的决定**：继续沿用窄屏“分类在上、内容在下”的现有系统，明确为均衡的两行网格或紧凑可滚动分类带；选择一种稳定节奏，保持选中项与内容标题的关联，不为每类另套卡片。

**验收**：760px 和 900px 临界处分类排列稳定，不出现孤立的末行项目；键盘焦点不会被横向裁掉。

位置：`apps/electron/compact.css .settings-layout/.settings-nav` 的响应式规则；`web/settings.mjs SETTINGS_PAGES`。

### N1 · Note：交付快照计数应当被解释，而不是被误当当前文件数

真实任务的“交付快照 4529 项”是历史存储事实，与“成员 5”并列后占据过高的注意力。建议明确为历次文件快照/版本数量，降为可查询的元信息；当前执行者和待处理原因优先。不要把它改造成未经业务验证的进度指标。

位置：`web/app.js workspaceDetailsMarkup`。

## 六个视角的结论

| 视角 | 结论 |
| --- | --- |
| 层级 | 目录与设置有层级；失败恢复场景 B1 阻断批准。 |
| 字体与颜色 | 系统字体、13px 正文及字重层级符合既有方向；路径动作的旧色与低对比需要修复，S3。 |
| 表面与深度 | 边线式深度、浅层次、无强阴影基本一致；没有理由推翻既有侧栏和圆角选择。 |
| 构图与节奏 | 员工卡片、短表单和窄设置导航存在分配问题，S1/S5/S6；不要求所有页面填满窗口。 |
| 状态、细节、动效 | 焦点环、原生 dialog、空态和减少动画已有基础；B2 是已复现的行为缺口。没有把尚未注入的错误状态判成通过。 |
| 结构、复用、文案 | 多选器已有键盘行为与原生 Popover，不能因为是自有组件就判失败；Tab 行为却在不同页面重复且不完整。团队枚举与路径旧色是明确的一致性遗漏。 |

未发现足以单独判 Blocker 的负 margin 布局补丁：屏幕阅读器隐藏元素的 `margin:-1px` 和头像重叠属于合理用途，不以文本搜索结果直接定罪。未要求为按钮增加缩放动效；高频桌面操作保持无动画可以是有意选择。

## 修改顺序与批准条件

先处理 B1/B2，再统一员工卡片与短窗口表单，随后完成长文本基线、路径动作、团队状态和设置导航。批准需要重新实际检查：失败页一眼可见恢复入口；三处 Tab 的键序一致；长名称不破坏属性行；两主题下动作可读；760×600 表单保留完整草稿与可达输入。本文的建议尚未实施，不能把报告本身当作 UI 已改善的证据。

失败恢复的层级对照稿另存于忽略的 `.data/design-review-comparison-20261108.html`（及同名 PNG）。左侧为当前结构复现，右侧为未实施建议，均不是更改后应用截图；不应把此示意稿作为实际产品验收证据。
